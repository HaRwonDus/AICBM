# AICBM — техническое задание и дорожная карта
Версия 0.1 · 05.10.2026

## 1. Цель и пользовательский сценарий
Пользователь выделяет область Minecraft и задаёт: «Построй район на своё усмотрение». Система анализирует территорию, самостоятельно проектирует район, проверяет план и строит его без персонажа-бота. Результат: связная сеть улиц, здания с доступными входами, общественные пространства, учёт рельефа и окружающей застройки.

Планировка не фиксируется заранее. LLM выбирает пространственные решения; геометрический движок уточняет координаты и проверяет ограничения. Параметрические генераторы создают здания; готовые шаблоны допустимы как один из источников, но не единственный.

## 2. Границы MVP
Minecraft Java Edition, один сервер и одна строительная задача одновременно. Выделение прямоугольника, стартовый участок до 128×128 блоков, сохранение существующих объектов, дороги, жилые здания, парк. Сначала поддерживается плоский участок; полноценный рельеф — следующий этап. Произвольные полигоны, город 1024×1024 и дообучение вне первого MVP.

Версия Minecraft и серверная платформа выбираются перед Java-интеграцией. Контракт Rust не зависит от Fabric/NeoForge/Paper. Реализация начинается с автономного Rust-ядра. Библиотеки и адаптер модели выбираются после проверки совместимости; конкретная Huihui-модель пока не определена.

## 3. Архитектура
Java bridge: выделение участка, снимок мира, команды строительства, прогресс и сверка блоков.
Rust orchestrator: задачи, снимки, модель, геометрия, валидация, компиляция в блоки и исполнение.
LLM planner: концепция, типы зданий, размещение, улицы, исправление ошибок.
Geometry engine: расчёт дорожных коридоров, кварталов, участков и размещений.
Building compiler: параметрические здания → пакет операций с блоками.
Storage: JSON на первом этапе; далее SQL для задач и событий, снимки/схемы отдельно.
Telemetry: Prometheus для работы сервисов, Grafana для наблюдения, MLflow для сравнения модельных экспериментов. Существующие сервисы используются повторно.

## 4. Данные
Region: world_id, dimension, прямоугольник XZ, пределы Y, selection_id.
WorldSnapshot: snapshot_id, ревизия, высоты, вода, занятые и защищённые участки, дороги у границы. Окружение считывается с буфером, запись разрешена только внутри выделения.
PlanningRequest: текст, region, snapshot_id, seed, лимиты, demolition_policy=preserve.
DistrictPlan: schema_version, plan_id, snapshot_id, концепция, улицы, кварталы, здания, входы, парки, материалы.
BuildBatch: job_id, batch_id, порядковый номер, ожидаемые исходные блоки, операции, checksum.

Начальный examples/plan.json — только структурный поднабор DistrictPlan: границы и здания. Полный дорожный и мировой контракт добавляется в следующих этапах. Координаты XZ используют полуоткрытые интервалы [min,max); высота здания — положительное число блоков. При выделении включённых углов Java переводит максимум в max+1 с проверкой переполнения.

## 5. Поведение планировщика
1. Получить снимок выбранной области и окружения.
2. Сформировать концепцию и объяснение решений.
3. Вернуть структурированный план, не произвольный исполняемый код.
4. Проверить синтаксис и геометрию.
5. Вернуть модели список конкретных ошибок; максимум 3 попытки исправления по умолчанию.
6. При исчерпании попыток завершить failed с отчётом, не строить некорректный план.
7. Скомпилировать проверенный план, сверить свежесть снимка и начать строительство.

Данные мира — факты, а не инструкции модели. Проверки обязательны для любой модели. Разнообразие достигается пространственными решениями, seed и параметрами зданий. Один seed сохраняет процедурный результат; точная воспроизводимость LLM обеспечивается сохранением ответа, а не обещанием детерминированного инференса.

## 6. Обязательные проверки полного MVP
Все изменяемые блоки внутри области и допустимых высот; валидные материалы; отсутствие пересечений зданий и дорожных коридоров; сохранение защищённых объектов; каждый вход связан с пешеходной сетью; улицы связны; нет строительства на воде без поддерживаемой конструкции; бюджет блоков соблюдён. Проверяется и план, и итоговые операции: крыша или декор не должны выйти за границы footprint.
Неподдерживаемый рельеф должен приводить к явному отказу или перепланированию, а не молчаливому выравниванию участка.

## 7. Исполнение и восстановление
Состояния: selected → snapshotting → planning → validating → compiling → building → verifying → completed; также failed, cancel_requested, cancelled и paused.
Команды bridge: capture_region, apply_batch, get_job_status, cancel_job. Сообщения имеют protocol_version, request_id, job_id, payload; ответы содержат status, error_code и результат.
Идемпотентность: batch_id и checksum записываются устойчиво; повтор того же пакета возвращает сохранённый результат, изменение checksum отклоняется. Пакеты выполняются на игровом потоке с настраиваемым бюджетом на тик. Отмена останавливает будущие пакеты, но не обещает автоматический откат.
Перед изменением сохраняется журнал исходных блоков. Откат не перезаписывает последующие пользовательские изменения: конфликты показываются отдельно. После сбоя сверяются журнал и фактическое состояние.
Перед исполнением проверяются изменения мира после snapshot. Для MVP изменённый участок останавливает задачу и требует нового снимка.
Bridge привязывается к localhost по умолчанию; удалённое соединение требует аутентификации и защищённого канала. Секреты не хранятся в репозитории.

## 8. Приёмка
На тестовом плоском участке 128×128 свободный запрос создаёт район с минимум 5 зданиями, связными улицами и парком. Все входы доступны. Ни одного изменения за границей или в защищённой зоне. Повтор пакета не меняет результат. Отмена останавливает новые пакеты. Разрыв соединения не теряет статус задания. Итоговая сверка учитывает ожидаемые состояния блоков, а не только ответ Java «успешно».
Набор минимум из 10 сохранённых участков/запросов используется для сравнения планировщиков. Для него фиксируются валидность планов, доля исправленных планов, доступность входов, затраты токенов, время и причины отказов. Целевые показатели производительности выбираются после базового замера на целевой VM.

## 9. Дорожная карта
Оценки в рабочих днях одного разработчика, без ожидания доступа и установки окружения; это ориентиры, не обещанные даты.

| Этап | Объём | Критерий завершения | Оценка |
|---|---|---|---|
| 0. Контракт и ядро | Границы, JSON, CLI, структурная валидация | Валидные/ошибочные планы проверяются тестами | 1–2 дня |
| 1. Java bridge | Выбор платформы, выделение, снимок, пакет блоков | Rust читает участок и строит тестовый объект | 3–5 дней |
| 2. Геометрия | Дорожный граф, участки, входы, проверка связности | Район без LLM проходит пространственные проверки | 4–7 дней |
| 3. ИИ-планировщик | ModelClient, structured output, ошибки и исправления | Свободный запрос даёт проверенный пространственный план | 3–5 дней |
| 4. Генерация зданий | Размеры, этажи, фасады, крыши, материалы | Разнообразные здания компилируются без выхода за границы | 4–7 дней |
| 5. Надёжное исполнение | Журнал, повторы, отмена, восстановление, сверка | Сценарии сбоя проходят интеграционные тесты | 3–5 дней |
| 6. MVP и QA | Метрики, 10 участков, отчёт, нагрузка VM | Все критерии приёмки выполнены | 3–5 дней |
| 7. Расширение | Рельеф, полигоны, большие районы, редактирование | Отдельная приёмка каждой функции | После MVP |

Минимальные проверки повторов и остановки нужны уже на этапе bridge; этап 5 доводит их до устойчивого восстановления. Полный MVP ориентировочно 4–7 рабочих недель. Дообучение рассматривается только после сбора ошибок и сравнительного baseline: промпт/инструменты против обучения на одинаковом наборе задач.

## 10. Уже начатая реализация
Создан Rust crate с JSON-моделью, CLI validate и 8 тестами. Проверяются границы, высоты без переполнения, ID, пересечения и защищённые области. Модель, дороги, Java и строительство пока не реализованы. Cargo/rustc отсутствуют в среде подготовки: тесты написаны, но не запущены. Первый шаг на VM: cargo test, затем cargo run -- validate examples/plan.json.
